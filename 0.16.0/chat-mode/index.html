    Chat mode: the conductor inside the engine¶

    In chat mode a TandemLLM engine loads TandemApp's conductor as its extension (QSE_MODE=chat, QSE_EXT=tandemapp.engine_ext, the engine extension interface in contracts/engine-ext-v1). This page is what the conductor does there: the TandemLLM model, the profiles and the router, the status lines and the narrator, the package library, Laya for the model's scripts and the session monitor. The overview is conductor.md. The engine's side, its hook points and what a headless engine answers, is in the engine's server.md.

    TandemLLM and the conductor¶

    With --conductor-config DIR (off by default; ops/start.sh passes serve.env's QSE_CONDUCTOR_CONFIG to the :8000 service only), the server serves one model, TandemLLM: the weights with a conductor in front (tandemapp/conductor/). /v1/models lists TandemLLM alone. The raw engine's name (--served-model, qwen38-spark-engine on the box) is a hidden alias: it is not listed, GET /v1/models/qwen38-spark-engine answers with TandemLLM's card, and a request that names it, or any other model, runs exactly as a TandemLLM request, so no client breaks. Every response carries X-Tandem (raw, shadow or on: the resolved profile's mode, which also caps the session monitor's mode below) and X-Tandem-Profile. The monitor runs the profile's task modes, caps and the thresholds that map onto its policy file. Every response, /health (with its cache block), the dashboard's System view and the Live stream say TandemLLM as the model; /health, the cache block and the System view give the base engine's own name as base_model. The usage ledger records model_served = TandemLLM for every request, beside the name the client sent (model) and the mode it ran in (conductor_mode).

    Raw is a header, not a model name. X-Tandem: raw (or the locked profile raw or bench named in X-Tandem-Profile) serves the release's path byte for byte: no class, no note, no effort change, the monitor raw. The one difference is where a plain API client's reasoning goes (SRV-617, above). Benchmarks and the paper's numbers use it (benchmarks.md for tool-eval-bench): tools/client_smoke.py --x-tandem raw and tools/session_replay.py --x-tandem raw send it, and tools/row3.py --no-server refuses a server that lists TandemLLM, because the atlas runner sends no headers (a server row3 starts itself runs without the conductor and is the raw engine). tools/flagoff_identity.py runs the engine in-process and is not affected.

    A request resolves to a profile: the X-Tandem-Profile header (an unknown name is a 400 with param: X-Tandem-Profile), else the profile mapped to the client (opencode gets coding, Open WebUI chat, the Hermes agent hermes, the Chat tab chat-app), else settings.tools_profile (tools) when no profile maps the client kind and the request offers a function tool with tool_choice other than none (an OpenAI SDK, curl, a benchmark; SRV-621), else settings.default_profile. The tools rule needs the profile in the store and no memory switch on it; tools_profile: "" turns it off. Its decision rows carry extra.profile_source: tools. X-Tandem: raw or shadow lowers the mode and nothing raises it. raw and bench are locked.

    The tools profile (SRV-621) is general with prompt: client: the engine reads the prompt the client sent, the raw path's ids. The plan drops its notes, cards, identity and memory lines, a moved tool description, a router budget and a closed think block, and journals them by kind (extra.prompt.dropped). No earlier note replays. Side requests and compactions go as sent, and a regenerate keeps the client's sampler. No class question and no effort decision run: the class question's side call cost a full tool-eval-bench run 1.23 times raw's time. Nothing else of the router runs: no packages or rules, no memory (the key is absent), no session transcript (transcripts: off), no state lines, no loop escape. D1, D1b, D2, E1, C3, C4 and C5 act, and each act is a journaled monitor event, so a request without one gets the raw request's prompt. The secret echo mask (SRV-625, under Session transcripts) is on; it changes the answer, never the prompt. A box with its own documents stores the profile at its next start (shipped defaults); a stored settings document without tools_profile reads it as tools.

    Before the request queues, the router decides which kind of task the turn is. A turn that only carries tool results keeps the session's class, and so does a tool's media that opencode sends as a user message right after the tool results (the caption Attached media from tool result: and the image or file, no text of its own; journaled kept: tool_media, SRV-161: before it, every photo3d session ran about 90 % of its turns as chat at low effort), so in an agent session only a new user message asks a model: the decider's choice question first (any model behind the Jev question shape: role decider, by default self, the engine's own decision models below, asked in process; engine:<family> names them too, and an HTTP endpoint another server's; used at 0.80), then the engine itself with X-Tandem: raw and thinking off and structured_outputs.choice (used at 0.55), else the session's class. No word list decides anything. The class sets the thinking budget, thinking off (the generation prompt's <think>\n becomes the template's closed empty block at the tail; the template renders reasoning_effort as the first system tokens and enable_thinking: false drops that sentence, so the router never re-renders), and a note with the effort sentence, a skill or package and rules. A class may list several packages: one marked general in the packages document (the coding package, 2026-10-02) goes in whole on every turn of the class, before the task skill, and so does one the class names in its policy's core (0.3.48-test, FX6: the class's defining skill, threejs-scene for three_d; a core name the class does not list is ignored, a profile's routing core replaces the class's). The router's second question (package_question) picks one among the rest, or none. On the prose classes its answer holds for the session's class (0.4.7-test, FX15, the class policy's package_sticky: class; the router's classifier.package_sticky is the default for a class without one, absent message): a later user message the class question keeps in that class takes the same package (how: sticky, no question, and its note is already live), and the question is asked again when the class question moves the session to another class. After an answer of none the question is asked again on the next message (VIS-119, QWEN38_PACKAGE_HOLD, pick, as 0.4.7-test did); answer holds a none for the class as well while the follow-up's candidates are among the ones it was asked over, and a turn with no answer (busy, a timeout, below the bar) holds nothing. The coding classes keep message, a question on every new user message, as 0.4.6-test did: an agent session's next message is often another task that wants another skill. UX3 measured 2.4k tokens a turn on the prose classes (34 options), 3.3 s when it missed its head on slot 0. Like the class question it runs on an idle side slot when slot 0 holds a conversation (_guest_of_slot0: up to --resident-guest-max tokens, sharing less than a chunk, whatever its share of the conversation's length), so it never writes over the rows the conversation's next turn resumes from. On 2026-10-06 "Create a new folder and create there a pagoda garden" went to three_d at 0.464 while threejs-scene was still one of those options: the question answered none at 0.747, no 3D skill went in, and the model built a flat SVG page. The question's Qwen stage gets the class question's prompt with the packages as the classes; a router's classifier.package_prompt replaces it, with {class} (the routed class), {question} and {classes}. Measured on 51 prompts (n = 1): three prompts that name the class (schema.PACKAGE_PROMPT_CLASS among them) cost 8 to 27 test-skill picks on code_edit and debug, and still left three of four unsure 3D prompts under the 0.6 accept, so none is the default. The journal row has extra.package_general, extra.package_core and extra.package_choice; a document without the flags is read as before. The packages fit the request's tools (0.3.50-test, SRV-243): the router reads what the tools can do off their schemas (signals.tool_caps: a shell is a tool with a command argument, opencode's bash, Open WebUI's terminal run_command; a file write is a tool with a path and a content argument), and a package names what its steps need in requires_tools (shell, write; absent: a shell when its text calls TandemLLM through {tandem_url}, since Laya, the library and the memory are reached with curl, else nothing). A package the tools cannot carry out stays out of the turn, or gives way to its fallback (the shipped coding to coding-answer: write each file complete, check it by reading), and the note says which tools the chat has and to deliver the files in the answer, in code blocks (router tool_fit.note_none, note_write). cards.harness and the library card need a shell too, and so do the memory's routes and its skill (SRV-247). A plain Open WebUI chat (search_web, fetch_url) asking for a landing page got the testing and Laya packages on 0.3.48-test: it called terminal and write_file ('Tool not found'), fetched the library's address with fetch_url and printed the page twice, 518 s. The row has extra.tools (offered, caps, dropped, fallback); tool_fit.mode: shadow journals what would go, QWEN38_TOOL_FIT=off keeps every package. The other direction (SRV-615): a package whose result an offered tool delivers stays out when the user wants it done. A package names its result in deliverable (send, schedule, post); when one is about to go in on a request that offers a client tool whose declaration makes the deliverable (signals.tool_effects, C5's reading: a recipient and a message, a time and a subject, or the name's verb; a post counts as a send), the class question's stages get one more question, "done with one of these tools, or the text itself?", with the tools' names and the first sentence of each description (tool_fit.deliverable_question, accepted at deliverable_accept, 0.6). tool keeps it out, text puts it in, so "draft an email to Sarah, I will send it myself" keeps write-message; with no answer it stays out (how: schema). Without such a tool (Open WebUI's search_web and fetch_url, opencode's tools) the package goes in and nothing is asked; a client that forces a function keeps it out unasked. The tool turns of the same user message keep the decision; a pin wins (kept_out_skipped: pinned). On tool-eval-bench's TC-03 ("let Sarah know the meeting moved to 3pm", get_contacts and send_email offered) the chat profile put write-message in at 0.995 and the model wrote a message to copy. The row has package_choice.kept_out (name, why: tool_delivers, deliverable, tools, how, p) and extra.deliverable_stages. It ships as tool_fit.deliverable: shadow, which asks and journals under shadow.tools.kept_out and keeps the package in; on acts and off asks nothing. With it on, the chat profile passed TC-03 and scored 91 as on 0.12.0, with TC-47 and TC-51 failing (n = 1, cause not tested); the counter is qse_conductor_package_kept_out_total{why,mode}. The tools profile has packages off and asks nothing. The reading line (0.3.48-test, classifier.reading, under the profile's classify decision): a class a model stage picked on the turn the class starts, below reading.below (0.8, the confidence a class switch needs), with another class at reading.other (0.15) or more, both with a reading phrase in the router document (three_d "a 3D three.js scene", design_ui "a flat web page", drawing "a 2D drawing"), gets one sentence in its note: build it as the picked class and open the answer with one short line such as "Building it as a 3D three.js scene. Say if you wanted a flat web page.", never a blocking question. The row has extra.reading; mode: shadow journals the sentence and adds nothing. The note goes into the last turn before its <|im_end|>, and later turns of the session replay it at the same token position, so the resident prefix keeps matching. A later user message's note carries only the parts (the effort sentence, each package, the rules) that no live note of the session holds with the same text (QWEN38_NOTE_DEDUP, parts): a coding message whose task skill differs from the last one's adds that skill, a few hundred tokens, not the whole note again. The replayed notes have a budget (injection.max_replay_tokens, 16,000), and over it the oldest note goes, which changes the prompt at that note's position, so the turn reads everything after it again. Before 0.3.47-test's second build the whole note came back with every new task skill (the general packages are about 4,800 tokens), and the third copy crossed the budget: live in an Open WebUI agent chat, a turn read 35,442 tokens again (49 s); replayed with one build, the fifth code message of a 20,000-token conversation read all of it (cached share 0.000, 60.7 s). block keeps the old rule for an A/B. The proxy follows the same rule. The router's session is the client's conversation id (opencode's x-session-id; Open WebUI's X-OpenWebUI-Chat-Id, which it sends when its connection to TandemLLM has the header X-OpenWebUI-Chat-Id: {{CHAT_ID}}, see operations.md), else a hash of the conversation's head: its messages up to and including the first user message, which every turn sends again. Every chat that opens with the same message has that hash, so until 0.3.48-test they were one session (SRV-225: a new Open WebUI agent chat's first row counted 27 turns and 21,216 session tokens of earlier chats and replayed their notes). Since 0.3.49-test a head holds a list of conversations: a conversation's very first turn (its one user message is the last message) starts a new one (h:<hash>#2 and so on) when the newest one of that head has had a turn, and a later turn finds its own by a hash of its whole first turn as the client sends it back (the first message, the answer, its tool calls and results), which two chats with the same opening do not share; the first turn's tool rounds stay with the newest. A first turn regenerated without an id is the same request as a new chat; it starts afresh, which costs it nothing (the class is decided the same way and the notes go in at the same place). The decision row's extra.session says how the session was found (id, new, continued, alias); QWEN38_SESSION_GENERATIONS=off is the old rule. Until 0.3.15-test it was the first two messages, and a chat with no system message (the raw model's, Hermes', Open WebUI's) became another session on its second turn, when the first answer is the second message: turn 1's note was not replayed, the prompt parted from the resident rows at the note, and the follow-up resumed from nothing (0.3.14-test's live check, 2026-10-02 22:07: cache_n 0 after a 1,413-token answer). It is never streamed, never counted in usage, never stored in the suffix store, and a request with a note skips the response cache. Who it is (0.3.43-test, SRV-191): on the turn whose message asks who or what the model is or which model this is (English, German, French, Spanish, Italian, Dutch; schema.IDENTITY_ASK), the router adds one more note, you are Qwen3.8-27B, running in TandemLLM, the engine and harness that serves you here; say that in one short sentence in their language, replayed at its place on every later turn of the session like the others (its own decision type, on under every profile that is on; QWEN38_MODEL_NAME names another checkpoint). The raw and bench profiles never see it, and a session that never asks carries nothing new. The Qwen stage (0.3.43-test, SRV-189) reads every class's probability off the answer's first token and its alternatives (top_logprobs), so the journal row shows the whole distribution; a code class below 0.7 for a request that names nothing of code and names a piece of prose (an essay, a letter, "700 words") is not taken, the best class outside the code classes is, and the stage row says guard. On the labelled sets plus 32 prose prompts (374 prompts, the live stage) it changed two answers, both essays routed as code_edit, and nothing else. A client's own number in any shape (max_reasoning_tokens, reasoning.max_tokens, thinking.budget_tokens and others) and its thinking off or on always win; its effort word yields to the turn's level (see Thinking budgets from the client). The budget is a real cap per effort level (SRV-159; before it medium, high and xhigh differed by their sentence alone): low 1,024, medium 8,192, high 16,384 reasoning tokens, xhigh none below the D2 backstop, off thinking off; a profile's thinking.budgets overrides a level (the journal's budget_source is then profile, else class). When the reasoning reaches the cap, the session monitor closes it at SP1 with the vendor's phrase hidden (texts.vendor_close, the path the D2 backstop takes): the model's context carries the phrase, the client receives </think> and the answer, and the journal has CLOSE_REASONING with task route and reason budget(N). Without a monitor that acts (none, shadow) or for n > 1 the cap is ThinkBudget's, whose phrase streams.

    A first message under the accept bar (0.3.51-test, SRV-255). The class question's answer below the Qwen stage's accept (0.45) used to send the turn to the profile's default class, chat, also when its top class builds something. Router v17 widened chat's description (SRV-235), and the request "Create a new folder and create there a pagoda garden" read three_d 0.378 (0.464 under v16): the turn went to chat, without the 3D skill, and the model wrote an ASCII pagoda into a file until the argument loop guard stopped it. classifier.below_accept (mode: default, the old rule, or build; margin) keeps a session's first classified message on its top class when that class builds something (its policy names packages: code_edit, debug, design_ui, drawing, three_d) and leads the second by margin; the row says kept: below_build. The shipped router has build and 0.1. On 341 labelled prompts (tools/class_fallback_eval.py, router v17's answers) the chat fallback had 307 right, the top class always 308 (two more right, one newly wrong), the top build class 309 (two more right, none newly wrong); 0.1 of lead changed none of them. A document without the key keeps the old rule.

    A class nobody decided (SRV-763). The Qwen stage asks the server's own port; when the server's estimate says the answer cannot come inside the stage's timeout the stage is skipped (qwen_busy), else it may run out the timeout (qwen_timeout). On 2026-10-31, with 8 Chat-tab chats at once, 92 of 113 turns fell back that way to the chat-app profile's default class, code_edit, at xhigh with 5,956 tokens of coding packages, and the package question then waited its own 8 s or was skipped too; the same prompts one at a time routed to research, plan and writing. With QWEN38_FAIL_OPEN=general (the default) a turn whose stages all failed, one of them by a load error (qwen_busy, qwen_timeout, qwen_http_429, qwen_http_503), asks no package or library question, in every profile. A session keeps its class and level. A profile that names an undecided_class (chat-app ships chat) gives a new session that class lean: at most the profile's thinking.default level, the class's general packages and core alone; its tool turns keep that note. A profile without one (coding, hermes, overnight) keeps its default_class's whole policy and stickiness on such a turn and only skips the two questions. A chat-app session whose answers all stayed below the bar takes the undecided class with its whole policy, unless the top answer's class builds (a second build class closer than SRV-255's margin): then default_class with its files-care, as before (extra.undecided_builds). A session whose class is such a guess counts as new to its next message: an answer replaces it even below the switch (extra.guess_replaced), a build class over the margin takes it (SRV-255), and a message the box was not too busy for runs the class's whole policy with the package question even below the bar. The row says extra.fail_open and extra.undecided_class; a missing classifier (refused, unreachable, its role off) still takes default_class on a new session (SRV-534). QWEN38_FAIL_OPEN=class is the old rule. A stored chat-app profile gets undecided_class by the migration 2026-10-31-chat-app-undecided-class. The estimate itself (_own_eta_ms) charges another slot a turn only while it prefills (the chunk it is on), decodes, or holds a request that has not reached its prefill (its prompt's rows, up to a chunk: a memory admission wait, the vision tower), or while TandemLLM's own job holds slot 0 (QWEN38_OWN_UNITS, prefill; busy, every busy slot a whole chunk, as before: the class question's slot in its end's bookkeeping read 3 x 3.8 s on an idle box), and reads the prefill rate of the requests that had the GPU turn alone from their lock to their first token (QWEN38_OWN_RATE, solo; all, every request's: after a burst it read 150 to 190 tok/s, against 969 alone). Its burst term, the other requests in the router or waiting for a slot, keeps every request's rate (QWEN38_OWN_BURST_RATE, peek; solo), since a burst's prefills share the GPU and a short estimate asks a question that then runs out its timeout. An asked stage's row carries eta_ms beside its ms (a cached row, cached: true, carries its first ask's).

    A compaction (0.3.21-test): opencode's compaction request is the class summarize (structural; thinking off, no package, nothing replayed) in both shapes it comes in: no tools, no system text and the history as one user message (2,000 characters or more), which counts only when the client is opencode (the ledger's client kind; since 0.3.41-test, SRV-175: a pasted document with "summarize" in a fresh chat from any other client has the same shape and was journaled as a compaction, thinking off, with the line "the conversation was compacted"; it is a plain turn now, its class decided like any new message), and opencode 1.18.34's, where its compaction agent's prompt is the system message (You are a context summarization agent. You are given a conversation between a user and an agent. at its head, signals.COMPACTION_SHAPES), the history as the one user message after it, no tools. Before 0.3.21 the second shape was routed as a design turn (seven packages, high effort, 2,116 reasoning tokens on 2026-10-03). The first user message after a compaction (continue, opencode's own Continue if you have next steps ...) keeps the session's class, journaled source: sticky, kept: after_compaction, and asks no classifier: the compaction carried the task over, and those few words are not a new task (continue was chat at 0.998, which has no package, and every turn after the compaction went without the design packages). The class's block is not in the compacted history (the prompt parts from the old note's position), so it goes in again as on a session's first turn, and the turns after it replay it. The next message a person writes is classified as any other. The same continue in a session that was not compacted is a new user message like any other.

    What a classifier reads (SRV-153): a digest of the new user message (its head and its tail), sized per stage (the decider's to its own limits(), (context_tokens - question_tokens) x 3.5 characters, 1,120 for Laya; Qwen's to the router's digest_chars), followed by one context line the router writes from what it already knows: prev=code_edit@0.93 tools=read,edit,bash files=.py,.md checker=calccheck:FAIL compaction=no (the session's class and confidence before this turn, the last three tool names, the extensions of the files the last eight calls named, the newest checker result, whether a compaction came since the last classification; none for what is not known yet). The line is at most 120 characters and comes out of the tail's share, so the digest keeps its size; it never holds a path, a file name or a file's text. classifier.context_line in the router document switches it, off by default: with Laya alone it failed SRV-153's ship rule (2026-10-01, Laya on the box CPU: the 216 short prompts answered right at the 0.80 threshold 50.0 % without it and 32.4 % with it, and of 12 follow-ups that change the task 10 were right without it and 1 with it, because the line pulls Laya to the previous class); the Qwen stage with the line is still to be measured. The journal's digest is the text the stages read and extra.context_line the line. Before SRV-153 the router built one 2,000-character digest and the decider cut it to its limit from the front, so on a long message it never saw the tail; sized per stage, Laya's best guess on the long set was right 33 of 60 times instead of 29 (requests at the tail 14 of 20 instead of 7), and its confident wrong answers went from 3 to 0.

    Qwen in the conversation (the in-context stage, 2026-10-02): a new user message in a long prompt or a follow-up is classified by the engine itself inside the conversation it already holds, instead of the digest cascade (Laya was confident on about 15 % of follow-ups and 22 % of long prompts). classifier.context_stage in the router document switches it: mode (off, the seed and every router stored before it; on), min_tokens (8,192: a prompt at least that long goes to the stage), followups (true: a user message after an earlier answer goes to the stage whatever its length), accept (0.55) and question. A short first message keeps the decider; a tool-result turn, a compaction, classify off and the test box never use the stage. Images in the conversation (opencode's screenshots in a photo3d or spiral session) go through it as the turn's prompt carries them: the stage expands every placeholder before its parting point into the same rows, rotary coordinates and key_ids the turn's prompt gets, and the tower's output comes from the embedding cache when the turn asks for it again (on the random vision model with an image in the history, the follow-up re-read 31 rows without the stage and 7 after it, bit-identical). Under the engine lock, right before the turn's own prefill, the stage prefills the turn's prompt as the client sent it with the session's earlier notes replayed (the prompt the resident prefix holds), cut after the last message's <|im_end|>, plus one hidden user turn (the question, one A: id - description line per class) and the template's closed think block, and reads the answer from the last row's logits: every class is a letter, a single token, so the softmax over the letters is the whole constrained answer (tandemapp/conductor/incontext.py, nothing decoded). It extends the resident prompt like any turn and takes its anchors on the grid; the turn then shares every token up to the insertion point and resumes at the grid line below it, so it re-reads at most a grid chunk plus its note and tail instead of everything since the previous prompt (on the random model, a turn that re-read 50 tokens re-read 18 after the stage, whose own prefill was 52; the turn's logits, recurrent state, KV rows, anchors and the drafter's rows equal the turn without the stage bit for bit, tests/test_context_stage.py). The stage takes the state store's prefix snapshots only at lines up to the parting point and no session snapshot, never streams, never counts in usage, never reaches the suffix store or the turn's context. The journal's stage is qwen_context with its label, confidence, every class's probability, ms, prompt_tokens (the stage's prompt), prefilled and reused (what its prefill forwarded and resumed), and reason (followup or long); the row's source is qwen_context, and extra.context_stage says why it was due.     The narrator writes the lines (ui.narrator, P1)¶

    With a profile's ui.narrator: on beside ui.states: on (the Profiles screen, off by default and absent from every stored profile), each state line is written by a small model inside the engine instead of the template: the narrator role, MiniCPM5-2B (QWEN38_NARRATOR_MODEL=minicpm5-2b, the checkpoint under QWEN38_NARRATOR_DIR). It is a plain Llama-architecture decoder in PyTorch (engine/generative/llama.py), BF16, eager, greedy, with its own tokenizer and chat template (thinking off) and its own KV cache of 1,024 rows; its greedy text equals transformers' LlamaForCausalLM on the same weights (tools/narrator_reference.py). It gets the step's kind, what that kind means and its facts in words (the class's label and the effort, a cap, the tools and files of a check, the counts) and answers with one line; nothing of Qwen but text reaches it.

    The limits: at most 14 words and 24 tokens, inside the role's latency_budget_ms (150 ms by default, the roles document), counted from the call to the last token; a request spends at most four budgets on its lines. A line the model cannot finish in time, at its token cap, with too many words or markup, or with an error, is the template (the journal row's extra.states[].narrator says why, with the milliseconds and the tokens). The model is not loaded at the start: the first narrated line starts its load through the residency planner (role narrator, a 6 GiB claim, never during a hold or beside a decision model's load) and is the template, as every line is until it is loaded. The roles document's narrator.mode says how it runs: on writes the lines, shadow keeps them in the journal only while the client sees the templates, off never asks it.

    It runs on the request's own thread when the line goes out (before the prefill for the router's line, between two of Qwen's rounds for the monitor's, after the last token for the tool checks): Qwen waits meanwhile, nothing of Qwen runs beside it, and the engine's lock is held at most the budget and one step a line. Its weights and cache live in a memory pool of their own on a stream of their own, left out of the engine's ceiling like the decision models'. A narrated line goes out framed as "\n› <text>\u2060\n\n": a WORD JOINER (U+2060, invisible and not whitespace) closes the text, so the strip takes a narrated line of any text, which no template matches, wherever it sits.     A profile's outcomes section (each switch off when absent, which is every profile stored before it) and the router document's optional outcomes section (the settings over the defaults in tandemapp/conductor/schema.py, OUTCOMES) drive the plan "Laya as the test judge, state snapshots, turn outcomes and the client protocol":

    judge off, shadow Laya asked on the narrowed cases after the request, journaled only
    retrieve off, shadow, on a low-quality or stuck outcome retrieves the package that fits the work

    The snapshot (tandemapp/conductor/outcomes.py) is built at the start of every request whose newest message is a tool result, before the router's effort, from the body alone: the calls since the last snapshot (a call is taken once, by its id; a session first seen mid-way counts only what came after its last user message), their results' heads and tails, the files written, the screenshots' hashes (of their base64, the same equality as the bytes') and sizes, a console read's levels, checker lines, exit codes, a test runner's counts, the tandem_state JSON a result carries and its diff, a scratch log's tail ({tandem_scratch}/*.log, or .tandem/*.log in a project from before 0.3.41-test).     The outcome is the first label of outcomes.order whose facts matched: no_visible_change (the same screenshot, the same output of an output tool, or the same state dump after a write), regression (a checker reading worse than the session's best, more failed tests than the same command had, a state key gone), error (a non-zero exit code, failed tests, an error-level console message, an error line in a run's output), low_quality (a failing reading at least low_quality.far of its limit away, or one gate failing low_quality.fails times in a row), surprise (a state number the router document names, e.g. lives <= 0; a test run of 0 tests; an empty write), stuck (no write and no better number for stuck.turns tool turns or stuck.minutes), tool_misuse (a tool that was not offered, a required argument missing, a call the client refused), test_faked (an evaluate script that assigns to a member of an object it did not declare: keys['ArrowRight'] = true, mario.x = flagX), environment (an OS error string: connection refused, address in use, no such file, permission denied, command not found), lost_context (the first calls after a compaction read none of the state files). progress when only progress facts matched, none when there was nothing to read. A read's text is never parsed for errors, and no fact is a word that decides what anybody meant. Every outcome is journaled (kind: outcome, task outcome) with its evidence, the effort and the note; the route row carries extra.outcome.

    Laya for the model's scripts (/v1/laya/ask, L1, 2026-10-03)¶

    The aim: the model reaches Laya through our provider, from the scripts it writes, to test any software. POST /v1/laya/ask (tandemapp/laya_api.py) is the small, stable shape a script needs, open like the chat API beside it (no key at the engine; the service is LAN-only behind the reverse proxy; a bearer a script sends is ignored): {question, choices | scale | neither, text | texts, threshold?, model?, deadline_ms?}. choices is a list of labels or {label: meaning} (2 to the model's 20); scale a list of 2 to 10 levels, lowest first; neither makes question a yes-no question. One text answers {label, p, sure, probs, model, ms, chars, read_chars, clipped} (a scale adds level and score, a yes-no yes); texts (at most api.max_texts, 16) answers {answers: [...], model, ms}, one forward a text. p is the label's probability and sure is p >= threshold (the document's 0.8 by default). Laya reads a window of its context less its question budget, 1,120 characters for laya-english: a longer text is cut by code to its head (a quarter) and its tail around [...], and the answer says so. It runs in the idle window, which is where a script runs, between two requests of its session; a caller that meets a running completion waits up to deadline_ms (15 s, at most 60 s), then gets 503 busy with Retry-After. Errors have the OpenAI shape, {error: {message, type, param?}}: 422 invalid_request_error (before any model runs), 429 rate_limited (api.rate_per_min, 240 texts a minute over every caller), 503 busy/loading/refused, 404 when off. The answers carry Access-Control-Allow-Origin: * and OPTIONS answers the preflight, so a test inside the page the model builds (the browser tool's evaluate script) can fetch it. GET /v1/laya prints the contract and the limits. The deciders document's api section (mode, rate_per_min, max_texts, max_chars, deadline_ms, threshold; absent: the defaults, on) and questions.laya_api (the model, auto) configure it, on the Deciders screen's "Laya for scripts" panel, which also shows the calls since the start. Every call is a journal row (kind: laya_api, task ask): the type, the labels, the number of texts and their sizes, what was cut, the answers' labels and probabilities, the model, the time, the client kind; the question as a hash and a length, never a text. The contract is laya-ask and laya-ask-texts. The packages laya-testing (general on the coding classes: what Laya is, the call, and that the model must ask it about its evidence before "done") and laya-scripts (general on code_edit and debug: the helper {tandem_scratch}/laya.py and recipes for seven kinds of work: logs, CLIs, APIs, pages, games, data, regressions) teach it; the five kind skills carry one Laya example each. Since 0.3.41-test (SRV-163) the helper and the curl example name the provider only as {tandem_url} (a package text that calls /v1/laya, /v1/library or /v1/memory at a literal address is refused at save), the helper exits 3 with one line when the call fails ("the call failed on this machine, your code is not the cause") and laya-testing tells the model to go on without the verdict instead of debugging the transport: on the Spark, whose trust store lacks the LAN's private root CA, the saved packages' literal https:// address had cost a session up to 42 % of its time in certificate debugging.

    The engine can serve small decision models itself (engine/decision/): models that answer typed questions over a text in one forward pass with calibrated probabilities. A question is a choice (one of N options), a score (an expected level) or a yes-no probability. Laya's three published checkpoints (Apache-2.0) are the models it serves: laya-english (ModernBERT-large, 512 tokens of state and question), laya-multilingual and laya-typed-decisions (1,024 tokens each). QWEN38_DECIDER_MODELS names the ones a server loads; empty, nothing of it is imported and its routes are absent.

    The conductor's session monitor¶

    --conductor raw|shadow|on switches the session monitor (tandemapp/conductor/monitor/). raw, the default, runs none of it: the output is the raw engine's, and there is no stall close either (a client's own max_reasoning_tokens still closes the block with the streamed phrase). shadow runs every rule and journals what it would do, and executes nothing. on executes, each task in the mode its policy gives it. off is accepted for raw. A request's X-Tandem: raw|shadow|on header can lower the server's mode, never raise it, and every completion response carries X-Tandem with the mode the request ran in. A request with n > 1 never acts (at most shadow).

    The policy is a file, --conductor-policy (default ops/supervisor.yaml): every task's mode (off, shadow, act), every threshold and every text. It is validated at start against ops/supervisor.schema.json (JSON Schema, draft 2020-12), which python tools/conductor_policy.py --schema writes from the rule registry; python tools/conductor_policy.py [file] checks a file.

    The monitor acts only at four safe points, from a fixed action set:

    safe point when actions
    SP4 (the notes' SP0) the prompt is rendered, before prefill PROMPT_TAIL_NOTE, SET_THINK_BUDGET
    SP1 a verify block is committed and yielded CLOSE_REASONING, GIVE_UP
    SP2 the model wrote its end token, before it reaches the client CONTINUE_HIDDEN, GIVE_UP
    SP3 the answer ended (SP2's moment) and its calls are held REPAIR_CALL, REGENERATE_CALL, GIVE_UP

    PASS is "nothing"; NOTIFY is out of band: the stall watchdog's watch sends it (below), never a request. What the client sees: a hidden close forwards the policy's phrase through the engine and streams only from the closer on (</think> in tags, nothing in reasoning_content); a hidden continue drops the end token and forwards the close phrase (inside the reasoning) or a hidden user turn with a nudge and an empty closed reasoning block (after it), and the answer follows in the same response; GIVE_UP is one visible sentence from the policy with finish stop. Caps: acts_per_request and acts_per_session_hour, and never the same hidden action twice in a row on one turn; beyond them an act becomes GIVE_UP. Tool calls are held only while a tool-call task can act (and never for a constrained request, tool_choice required or named: the grammar writes those calls).

    A call written inside the reasoning (0.3.46-test, SRV-199): a turn of a request with tools that ends with complete <tool_call> blocks inside its reasoning, with nothing but whitespace (and the closer) after them and no answer, used to finish stop with no call and no text, because the parser reads the answer only (an Open WebUI agent chat stopped after "Let me see the full report"). E1 now has a case C: when every such block parses and names a tool the request offers, SP2 forwards the closer (the newline before it hidden, nothing when the block was already closed) and then the model's own call tokens as the answer, so the client receives the calls the model wrote, through the same parser and checks as any other, with no generation in between; the model then writes its end token. A block that does not parse or names another tool is case A or B as before, and two failed tries end in GIVE_UP's visible sentence, never a silent stop. E1 acts in the chat (Open WebUI) and general profiles too; a box whose stored profiles predate this sets E1 to act on the Monitor screen. On the reference box's ledger, 7 days before the change: 1 such stop in 322 Open WebUI rounds.

    Tool-call checks (SRV-113)¶

    With a tool-call task able to act, every call of an answer is held until the answer ends; a block that does not parse is held too, not let out as content. At the end token every call is checked by every SP3 task, before any is released:

    task rule what it decides wave 1
    C4 malformed_call a block that does not parse: a deterministic fix (REPAIR_CALL: JSON with trailing commas or Python literals, an unquoted name=, a </parameter> that never came) or a hidden reminder with the parser's reason (REGENERATE_CALL, at most regenerations a request, then the block goes out as content as without the checks); the arguments against the tool's JSON schema (required keys, types); a call the token limit cut (GIVE_UP, never half a call) act; the schema check in shadow
    C3 repeated_call the same name and canonical arguments as the previous repeats - 1 calls of the current user turn, whose results (from the request's tool messages) were identical, none of them a wait (wait_s): "do something different" act
    C5 sequential_mutations two or more calls to tools that change something outside the conversation (kinds: send, schedule, create, write, delete): "one action at a time: the first, its result, then the next" (REGENERATE_CALL, at most regenerations (1) a request) shadow; act in tools
    C1 risk_floor the floors, a list in the policy: rm -rf outside the project root, git push, a write outside the root, a download piped into a shell; the root is the working directory opencode states in its system prompt shadow
    C2 project_rules what text alone can decide of AGENTS.md (only when the system prompt carries it): a numbered copy of a file the session used, a path under /tmp/, a written file over 400 lines; a call whose every path is on allow_paths is exempt from all three (default /tmp/opencode, opencode's own scratch; a path covers everything under it, * ? [ make a glob, ~ is home, a relative entry is under the project root) shadow

    If all pass, the calls go out whole, each in one delta with an id made at release and indexes contiguous from 0. If any act fails, none goes out: the end token is dropped, a hidden turn shaped as the calls' tool result (templates.regen_turn) carries the reminders, and the model writes the set again in the same response; the client receives only the new calls, at index 0 again. An answer that ended without its end token (the token limit, a stop string) cannot be written again, so there a failure gives up. A block the client's own stop string cut is not a failure: C4 lets it out as the text it was (cut_by_stop), as the raw engine answers; only a block the token limit cut follows C4's cut (give_up). A profile turns each check's pack on or off (toolgate.risk, project, same_call, malformed, sequence) and sets its mode and thresholds. With the monitor raw, or no tool-call task able to act, calls stream as they always did. When the generation ends inside a block that streamed live (the token limit, the deadline, an end token inside a value), the block's text is not sent again as content: the client keeps the calls the stream closed and the open call as it was sent, with arguments that never close (until 0.3.31 the text went out a second time, and the next prompt carried it twice). A streamed request with stop strings is the one exception, with or without the monitor: its calls go out whole when their block closes, because a stop string can end the generation inside a block, and arguments already streamed cannot be taken back; such a cut block is the text it was, as in the non-streamed answer.

    C3 in detail (SRV-473). A repeat is the call that would be the repeats-th (3) in a row with the same tool and canonical arguments (key order and whitespace do not count), after repeats - 1 results with the same content. Only the calls after the last user message count: a user message starts over. A run whose result came back after the client took wait_s (10 s) or more, from the end of the answer that issued it to the request that carried the result, is a wait (a poll of a running job) and breaks the streak (the session monitor keeps that time per call id). A test run again after an edit, or a file read after a write, has another call in between and passes. C3 can only fire on a request whose turn already ends with the streak, so it holds calls only there: with C3 the only tool-call task that acts, every other request streams its calls live, as with the pack off. Past the caps a finding gives up: no call goes out and the turn ends with texts.give_up. The shipped coding, chat-app, hermes, overnight and chat profiles have toolgate.same_call: true (chat's C3 acts too); general has it off. A box's stored profiles get it once at the next start (migration 2026-10-14-<name>-loop-guard), unless a stored version of the profile ever had it on: then the current value stays.

    C5 in detail (SRV-623, policy 8). A call counts as a mutation when its tool's declaration says so (signals.tool_effects, the way SRV-243's tool_caps reads it; the messages are never read): send is a recipient parameter (to, recipient, channel, chat_id, ...) with a message parameter (body, message, text, content); schedule a time parameter (date, datetime, start, due, ...) with a subject (title, summary, subject, message, text); write a path with a body (SRV-243's write); create and delete the operation the tool's name opens with (after an MCP server prefix; its description's first word when the name states none: create, add, set, update, ... and delete, remove, cancel, ...). A name that opens with a read verb (get, list, search, read, fetch, ...) is a read whatever its parameters, as is an annotations.readOnlyHint of true; destructiveHint true is a delete. A shell is none: opencode reads through bash, often several calls at once. tool-eval-bench's send_email, create_calendar_event and set_reminder are mutations; its other nine tools, opencode's read, glob, grep, bash and webfetch, and Open WebUI's search_web and fetch_url are not; opencode's write and edit are writes. The check decides once an answer, at its second mutating call: two reads (TC-27), or a read beside one mutation, pass. The regeneration is C4's (templates.regen_turn); the client receives only the new calls. Its finding is about order, not a call that cannot run, so past regenerations, past the request's or the session's caps, and on an answer without its end token the calls go out as they are, journaled (fallback(regenerations=1), released(<cap>), ended(mutations=N)), never a give-up. C5 holds calls only on a request that offers a mutating tool. A constrained request (tool_choice required or named, or SRV-619's calls-or-document grammar for response_format with tools) holds nothing and journals C5 in shadow, as every SP3 act. Shipped: tools acts; coding, chat-app, hermes and chat journal it (toolgate.sequence: true, the task in shadow); general and overnight have it off. A box's stored profiles get it once at the next start (migration 2026-10-19-<name>-c5) when they have neither the task nor the pack; a stored monitor document gets the task with tools/monitor_migrate.py --put http://127.0.0.1:8000 --tasks C5.

    SP4's splices touch the prompt's tail only, so the resident prefix and the state store stay valid: a note goes into the last message just before its turn end (the template refuses a system message that is not first), and thinking off replaces the generation prompt's open <think>\n with the closed empty block the template writes for enable_thinking: false. Neither changes the system turn or reasoning_effort, which render as the prompt's first tokens.

    Hidden tokens are excluded from usage's counts in the default client mode (completion_tokens counts streamed tokens, prompt_tokens what the client sent; the prompt's hidden tokens are prompt_tokens_details.hidden_tokens, see Streaming). Engine usage mode includes hidden prompt tokens in the occupied context count; hidden output tokens remain excluded from completion_tokens. Hidden tokens are never in the suffix store, and a response the monitor acted on is not stored in the response cache. The KV holds them, and until 0.3.14-test every turn re-read the previous turn's whole output: the resident prefix anchored prefill chunks only, and the session snapshot that would hold the state after the generation is over the store's entry cap for any long session. From 0.3.14-test the resident prefix keeps an end anchor at the end of every generation (--end-anchor, on), and the hidden tokens are put back into the next prompt where the rows hold them (after the router's notes, before SP4), when the prompt then starts with every token up to that anchor; the turn forwards only its new messages (caches.md). Put back, they stay hidden: excluded from client-mode prompt_tokens, the suffix store and the response cache; the journal row has extra.end_replayed.

    Sessions: the conversation id the client sends (conversation_id, session_id or user in the body, X-Conversation-Id, opencode's x-session-id); else a compaction request (no tools, one user message) joins the most recent session and the next unseen prefix joins it too; else a hash of the first lineage_tokens prompt tokens, joined within join_window_s. The state is an LRU of max_sessions, with tool calls and results as hashes, never text.

    Every decision is one journal event and one [conductor] log line (task, decision, reason, counts; never a text).

    The claim check (E2, 2026-10-02)¶

    In three Mario sessions on 2026-10-02 Qwen ended with "Done … verified in-browser" after a test that set keys['ArrowRight'] = true instead of pressing a key, read "lost all 3 lives in 1.5 s" as "the damage system works", and teleported Mario to the flag to test the win. E2 (claim_check, tandemapp/conductor/monitor/claimcheck.py) checks such a claim before the end token reaches the client. The trigger is structural: the turn's class (the router's, RequestEvent.cls) is in classes (code_edit, debug, design_ui, three_d, drawing), the request offered tools, the model wrote its end token after a non-empty answer with no tool call (an empty one is E1's), and the session has a write behind it (a write_tools call in the request's history, or one the monitor recorded). Once a request; after per_session (2) notes on one session the event is claim_check_exhausted and the message goes out as written. No word of the answer decides anything structural.

    Then Qwen itself answers, thinking off, one letter a question: Q1 (claim_question), does the message tell the user the work is finished, working or verified (claim at claim_at, 0.85, or above); on a claim, Q2 (evidence_question, {since} the tools called since the last write), what the tool evidence since the last write says: supported, no_run_after_last_write, errors_in_evidence, surprise_unexplained or test_faked (taken at admit_at, 0.6). The router's Qwen stage cannot be used: it calls the server's own port, and at SP2 the request holds the engine lock, so the call would wait for its own lock until it timed out. The questions are asked in place instead, as the in-context stage asks its own (one letter a token, the softmax over the letters of the last row is what structured_outputs.choice leaves): the loop hands SP2's pending action to _force_close, where the KV holds the whole context and the end token was not taken; _ask_in_place settles the recurrent state as cache.capture does, copies it, forwards the hidden user turn (templates.hidden_turn with the question) after the KV's rows, reads the letters, and copies the state back and resets the KV's length (the rows above it are written over by the next forward). The drafter, ctx, usage and the client never see it. An answer other than supported continues the turn hidden at SP2 with that answer's notes text, as E1's hidden user turn: the end token is dropped, the note and the empty closed reasoning block are forwarded, the model goes on in the same response. Every other way out takes the end token as it was drawn, so the client receives what it would without the check: no claim, supported, an answer below its threshold, a failure of any kind (fail-open, claim_check(error:<why>)), the caps (acts_per_request, acts_per_session_hour; the check is not even asked when they leave no act), no room for the note, shadow. A request that records logprobs is never asked (its end token's row would be lost; claim_check(not_asked)).

    The journal row (task E2, tier 1) has both answers with every option's probability, the structural twin (twin: no_run_after_last_write when no call after the last write matches run_tools, else ran), the since list, the class and ms. Every note, sent or in shadow the one that would have been, opens an outcome: once label_calls (8) tool calls followed it, or the next claim check of the session triggered, a PASS row at sp label (claim_outcome(fixed|ran_no_fix|no_run)) says whether a run-like call and a write followed and whether the claim came again; a fix after a note is a true positive, a run with no fix and the claim again a likely false positive. The policy file has E2 in shadow; a profile's tasks.E2 sets its mode (shipped: acting in coding, hermes and chat-app, shadow in overnight) and its claim_at and admit_at. A server whose stored monitor document predates E2 runs none of it until a version with the task is stored. With E2 off, or not triggered, every byte is the release's (tests/test_claim_check.py: off against no task over the handler, shadow and a supported claim against off on the chain, the tree and the single-token step, the engine's state equal before and after each question). On the served kernels (the fused GDN commit, a commit pending into the next verify, the verify graphs) tools/claim_identity.py asks the questions at each moment SP2 can meet (a partial accept and its rollback, a full accept, a tree commit, a decode step) and requires every later logit and state to be bit-identical to the run without them; it needs the GPU, so a hold runs it before E2 is switched on.

    Observability (SRV-115)¶

    One journal for the router and the monitor: the table conductor_events in the usage ledger's file (schema version 2, migrated in place at start, every old row kept; python tools/ledger_migrate_check.py LEDGER tries it on a copy), written from its own queue thread, never on the decode thread. A router row (kind route) per TandemLLM request; a monitor row (kind monitor) per decision with its task and tier, its mode and rule, its reason and action, the hidden text (stored once in conductor_texts by its hash), its tokens, its position and the reasoning tokens at a cut; the request's outcome fills its rows when it ends, and the next request's checker result (RESULT: PASS|FAIL <- ...) fills next_checker. Checks that find nothing are counted, not stored (an answer whose calls all passed is one row, journal.tool_passes). Rows and texts older than 30 days go nightly, and the ledger's weekly backup leaves both tables out. With the ledger off the journal lives in memory; with the conductor raw nothing is written.

    The ledger's requests gains conductor_acts, conductor_hidden_tokens and conductor_acted; the dashboard's speed figures leave out the requests the conductor acted in. Prometheus (qse_conductor_*, METRICS.md) counts every decision, passes included, the actions, the hidden tokens, the gave-ups, the tier 1 questions and their failures, and the reasoning tokens cut. The live event (contract 1.2) carries activity.conductor on a watched request, with supervising while a hidden forward runs. GET /v1/conductor/events lists the monitor's decisions, and a session's timeline and export hold both halves.

    Extending it¶

    The interface the conductor's policy engine builds on, kept stable:

    • A rule: tier0.register(name, safe_point, params, required, doc) on fn(event, task, sup) -> Action | None. params is the JSON Schema of the task's parameters; the policy schema picks it up. A task in the file names the rule (rule: name) and carries its parameters, texts included.
    • The events (tandemapp/conductor/monitor/observe.py): RequestEvent (SP4, and sup.req at every later point: messages, tools, tool_choice, n, prompt tokens, in_think, max_tokens, the client's own budget, the client kind, whether a grammar constrains the answer, the profile), BlockEvent (reasoning tokens, inside, the detector arm that fired, the history arm's share, the position), FinishEvent (inside, the answer so far, the position), ToolCallEvent (name, arguments, index; for a block that does not parse its text and the parser's reason; the tool's schema; final when nothing can be written again).
    • An SP3 rule returns REPAIR_CALL with detail["arguments"] (a call) or detail["calls"] (a block that did not parse), REGENERATE_CALL whose text is the reminder, GIVE_UP, or PASS with a reason (an observation); detail["mode"] lowers what one finding may do. Supervisor.check_answer(items) runs them; release_call / release_block hand out what goes.
    • Action(kind, reason, text, budget, score, detail) from policy.ACTIONS. SET_THINK_BUDGET with budget=0 turns thinking off; with budget=n the request's reasoning closes after n tokens with the action's text, which must contain the closer.
    • Monitor(mode, policy, tok): .begin(mode, req, prompt_ids, conv_id) gives the request's Supervisor (None when raw), .reload(policy) swaps the policy for requests that start later, .mode_for(header, n) lowers a mode. A supervisor's .session is the session's state; .memo is a rule's per-request scratch.
    • The journal: Journal.write(event); Journal.sinks are called with every event (the SQLite journal's monitor_sink, Prometheus's on_conductor_event), and with three bookkeeping events: OUTCOME (the request ended), LABEL (a later checker result), COUNTS (the checks that found nothing).
