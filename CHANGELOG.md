# Changelog

Releases of TandemApp: the dashboard, the controller (`tandem-app`), Chat (chatd), the conductor and TandemNode. Until TandemApp ships releases of its own it ships with the engine's; the section below is TandemApp's part of the engine's Unreleased section, taken over when the docs were split (ENG-413). Older releases are in the engine's [CHANGELOG.md](https://github.com/TandemLLM/TandemEngine/blob/main/CHANGELOG.md).

## Unreleased

### The engine without TandemApp

- The engine carries no copy of TandemApp any more (ENG-413). TandemApp pins the engine's contracts at engine API 1.8 (`contracts/engine-api-v1/PIN`, `proxy.engineapi.SPEAKS`). In 1.8 the page, the Chat tab's forward and the other backends are this tree's controller's only: an engine answers them 404.
- The extension registers no `/dashboard` route. Its routes are the conductor's, the library, the model's memory and Laya.
- `tandem-app import-backends --from <file>` copies an engine's old relay database (its `QSE_BACKENDS`, ENG-413 WP14b) into the controller's: each backend it does not have yet, with its key under the controller's master key, its models (prices and switches included) and its routing rules. Without `--write` it shows what it would copy and writes nothing; `--disabled` stores the backends off. The users stay in the old file (`TANDEM_API_USERS_FROM`), and the old file is never written. [docs/proxy.md](docs/proxy.md#moving-from-the-engines-relay) has the steps.
- The Backends page on an engine says that no engine relays since engine API 1.8, and how to run the controller and bring an old relay's backends over, instead of asking for `QSE_BACKENDS`. The Setup page's mocks and e2e have no "Other backends" tool: the engine's Setup Guide dropped it.
- `tools/pair_suite.sh ENGINE OUT` runs the engine's pair tests, the engine with this tree's extension, against an engine checkout at the pinned commit.
- New here from the engine: `tests/test_static.py` (the page's files), `tests/test_doc_words.py` (no model count, no bird words), the manual's conductor part (six chapters), and four tools that call the conductor's routes (`argloop_live`, `library_install`, `memory_replay`, `playtest_install`). The setup mocks link the engine's README for the other backends.

### TandemApp

- Chat sandboxes can run as Kubernetes pods (SRV-863): with the Helm chart's `sandbox.mode: kubernetes` chatd makes each chat's sandbox a pod in the release's namespace through the API (a Role of pods, exec and logs there), with today's lockdown and limits, a user namespace and a 512-process limit per pod, the chat's folders as subPath mounts of the release's volume, and no network but chatd's egress proxy (a NetworkPolicy; chatd checks at start that the cluster enforces it and offers no sandbox when it does not). An out-of-memory kill, an eviction, a pod with no room and an image the node lacks each say so on the call; orphan pods go at start and once a minute. `ops/sandbox/build-k8s.sh` builds the image inside the cluster and imports it on the node, with no registry. [docs/chat.md](docs/chat.md#sandboxes-as-kubernetes-pods) and the chart's README have the design.
- A sandbox killed at its memory limit says "out of memory" on Podman and containerd too: chatd reads the kill count from the cgroup the container's first process is in, not only from Docker's two layouts.
- A Split starts and serves from TandemApp (SRV-817): one model cut across two Sparks. The planner asks each Spark's engine for its estimate with the `split` block (engine API 1.2), picks the cut whose smaller headroom is largest, and states every number, the link and why each other cut lost. The two Sparks need an interface pair in one subnet: a fabric pair first, a LAN pair with a warning, because the data link is neither signed nor encrypted after its handshake. A start hands a link key to both node agents (each keeps it in a 0600 file), starts the front stage, then the tail, checks both stages and the link, and routes requests to the tail alone. A link that drops makes the deployment degraded: requests get 503 `stage_down` with `Retry-After` until the stages link again by themselves. Stop takes the tail first and removes the key. The controller does not switch a Spark's weight profile: set each Spark to the pack first. [app/docs/proxy.md](docs/proxy.md) has the rule and the states.
- The Models page shows a Split as two stage bars with the link between them, its plan before the start, and plain words for the degraded and half-running states (VIS-272). Simple and Advanced choose how much of the plan shows.
- The standalone dashboard and proxy is TandemApp, and its command is `tandem-app` (OPS-238). `tandem-dash` still runs it with the same arguments and exit codes, after one line on stderr, and is removed in 0.17.0. The image is `tandemllm-app` from `app/packaging/Dockerfile.app`, its volume `tandem-app` and its env file `app/packaging/app.env.example`; [app/docs/proxy.md](docs/proxy.md#in-docker) says how to mount or copy a `tandem-dash` volume.
- The OpenAI routes can run through TandemApp's controller in front of the engine (SRV-733): `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/responses` and `/v1/models` answer as the engine does (its cards and decision models, any model id with `TANDEM_DEFAULT_BACKEND`, the client's headers on, the engine's keys with `TANDEM_API_USERS_FROM`), a request the engine still works on is never cut by the relay's timeouts, and each request is one row of the controller's ledger with its Spark, joined to the engine's row by the answer id (ledger schema 12). [app/docs/proxy.md](docs/proxy.md#the-data-plane-clients-through-the-controller) has the reverse proxy's locations and the rollback.

### TandemApp in its own directory

- TandemApp is its own package in `app/` (SRV-747): the distribution `tandemapp`, with its own version in `app/VERSION` (0.15.0; `tools/release.sh` writes it next to `VERSION` while one release ships both), installed from a checkout with `pip install ./app`, or `pip install './app[host]'` for psutil and NVML. The root `pyproject.toml` is gone. TandemApp's code imports nothing from the engine (`server/`, `engine/`), and `app/tests/test_import_boundary.py` holds that (SRV-748).
- The API TandemApp uses from the engine is a contract the engine owns, `contracts/engine-api-v1` (TandemApp pins a copy to an engine commit): the routes, `/health`, the engine's own reads, its metrics, its tool-call parsing, the Setup Guide's estimate cases and limits, and TandemNode's control of the engine. The engine's `/health` carries `engine_api` (`1.3`: 1.1 adds `GET /v1/replica/identity`, 1.2 the estimate's optional `split` block and `/health`'s optional `stage` block of a split model, 1.3 moves the contract to the engine and marks the routes that leave it, with no answer changed); an engine that does not send it speaks 1.0, and TandemApp takes any 1.x. Beside it, `contracts/engine-ext-v1` 1.0 is the interface for code that runs inside the engine's process (TandemApp's conductor in chat mode): closed at start, open per request.
- A Replicas deployment checks its members (SRV-741): each engine's identity (engine API 1.1) through TandemNode, every field but the window compared, a member that differs is `mismatch` and the field is named; an output canary every 10 minutes and after any member change, where a near tie counts only as a warning when one engine flips on it itself; a request past one member's window goes to a member that fits, else 400; `/v1/cache/peek`, `/prewarm` and `/release` go to the member that holds the conversation. An engine on 1.0 keeps the release and weights check. [app/docs/proxy.md](docs/proxy.md#deployments-placement-and-weights) has the rules.
- A deployment names the engine API version it needs: a member whose engine speaks another major is `down`, and the node's engine view `unhealthy`, with a reason that names the major this TandemApp needs; starting a deployment on such an engine fails at once.
- TandemNode's placement estimates come only from the engine's Setup Guide (`/v1/setup/estimate`). Add Spark's check reads TandemNode's version only, so a box with an engine checkout and no TandemNode reads `not installed`.
- Add Spark's engine step and the fleet update take the engine installer from `TANDEM_ENGINE_INSTALL_SH` only. The engine ref is `TANDEM_ENGINE_REF`, else `v` and the `VERSION` file beside the installer, else `v` and TandemApp's release. Without the variable, Add Spark's engine step fails and names it, and the fleet update skips each node's engine step.
- Node wheels are named `tandemapp-*.whl`.
- The `tandem-dash` alias stays until TandemApp 0.17.0, counted on `app/VERSION`.
- TandemApp's tests live in `app/tests` with their own runner, `app/tests/script_suite.py`. Since OPS-250 GitHub runs them in TandemApp's own `tests` workflow, as the `app suite` check, with `.[host]` installed and no torch; the engine's CI no longer runs them.
