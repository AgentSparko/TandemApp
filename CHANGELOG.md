# Changelog

Releases of TandemApp: the dashboard, the controller (`tandem-app`), Chat (chatd), the conductor and TandemNode. Until TandemApp ships releases of its own it ships with the engine's; the section below is TandemApp's part of the engine's Unreleased section, taken over when the docs were split (ENG-413). Older releases are in the engine's [CHANGELOG.md](https://github.com/TandemLLM/TandemEngine/blob/main/CHANGELOG.md).

## Unreleased

**Upgrading: an install that other devices reach and that had no password now answers 401 on every route but `/health`, the page and the sign-in until someone makes the owner with the setup code (SEC-28).** The code is single use and opens only the first-run setup. Get it from the controller's log (each start without an owner logs a fresh one, valid 24 hours), from `tandem-app users setup-code` on the controller's machine (on Kubernetes the `kubectl exec` line `helm status` prints under NOTES), or on Kubernetes from the chart's Secret (`kubectl get secret <release>-tandemapp-admin -o jsonpath='{.data.admin-token}' | base64 -d`; after an upgrade it holds the old admin token, which works once as the setup code). A bare process bound to 127.0.0.1 with no password stays open to this machine's browser only (local mode); a client on that machine that sends a made-up API key now gets 401: send none, or an API token. An install that had an admin password keeps it: it signs in as the account `owner`. One that had only an admin token takes that token once as the setup code.

### The sign-in

- Accounts, sessions and API tokens are the only sign-in (SEC-28); `TANDEM_AUTH` is read by nothing. Gone: the shared admin token as a bearer and as a password, `TANDEM_API_KEYS` and `TANDEM_API_USERS_FROM` as live key lists, the rule that everything is open while no password is set, the dashboard login switch (`TANDEM_DASHBOARD_LOGIN`, `--dashboard-login`), the loopback peer as the admin (`--trust-loopback`) and the `qse_dash` cookie. Their values are imported once at the first start: `admin.json`'s password becomes the account `owner`, each key an API token with the same hash (to confirm under Access), the admin token a management token that ends after 30 days and never signs in, and the OpenAI API's exposure starts at "network" when keys existed. A variable or flag that is left is named on the health page (`legacy_env_set`, `legacy_env_invalid`) and never stops the start.
- Going back to the release before works on the same state: its tables are untouched, `admin.json` follows the first owner's password, a key revoked here is disabled there too, and once a token exists the old key table holds a key nobody has, so the release before refuses requests instead of opening them.
- `/v1/dashboard/session`, `/v1/fleet/session`, `/v1/chat-app/session` and `/v1/fleet/app/password` stay one release over the accounts: their sign-in is the first owner's password, and `password_set` in their answers means a sign-in is needed.
- The installer writes no admin token: beyond loopback (`--listen`) or with `--behind-proxy` it prints a setup code while no owner exists, and it leaves the lines of an older install in `app.env`. The Helm chart's `auth.mode` is `accounts`; `legacy` is refused with a message.
- A client's `Authorization` or `x-api-key` never reaches a backend: the gate checks it and removes it.
- A move of the controller to a Spark gives the new controller's account `owner` the move's password and nothing else: the Spark keeps only its hash, and it never becomes an admin token or a token for scripts.
- The Usage and request views show a reader without the right `users` no other account's username: the user list and a request's user say "another account", and `user=` takes only the reader's own (SRV-873).

### The engine without TandemApp

- The engine carries no copy of TandemApp any more (ENG-413). TandemApp pins the engine's contracts at engine API 1.8 (`contracts/engine-api-v1/PIN`, `proxy.engineapi.SPEAKS`). In 1.8 the page, the Chat tab's forward and the other backends are this tree's controller's only: an engine answers them 404.
- The extension registers no `/dashboard` route. Its routes are the conductor's, the library, the model's memory and Laya.
- `tandem-app import-backends --from <file>` copies an engine's old relay database (its `QSE_BACKENDS`, ENG-413 WP14b) into the controller's: each backend it does not have yet, with its key under the controller's master key, its models (prices and switches included) and its routing rules. Without `--write` it shows what it would copy and writes nothing; `--disabled` stores the backends off. The users stay in the old file (`TANDEM_API_USERS_FROM`), and the old file is never written. [docs/proxy.md](docs/proxy.md#moving-from-the-engines-relay) has the steps.
- The Backends page on an engine says that no engine relays since engine API 1.8, and how to run the controller and bring an old relay's backends over, instead of asking for `QSE_BACKENDS`. The Setup page's mocks and e2e have no "Other backends" tool: the engine's Setup Guide dropped it.
- `tools/pair_suite.sh ENGINE OUT` runs the engine's pair tests, the engine with this tree's extension, against an engine checkout at the pinned commit.
- New here from the engine: `tests/test_static.py` (the page's files), `tests/test_doc_words.py` (no model count, no bird words), the manual's conductor part (six chapters), and four tools that call the conductor's routes (`argloop_live`, `library_install`, `memory_replay`, `playtest_install`). The setup mocks link the engine's README for the other backends.

### TandemApp

- Accounts and server-side sessions, behind `TANDEM_AUTH=accounts` and off by default (SEC-22, SEC-24). Four roles (owner, admin, operator, viewer); one table gives every route a permission, and a route without one is refused. A local identity provider checks scrypt hashes per account (PBKDF2 where Python has no scrypt). Signing in at `/v1/auth/session` makes a session whose id the database keeps only as a hash; it ends after 30 idle days or 180 days in all (both settings, at most 400), at once when revoked, and its open streams close with it. Every write with the session cookie comes from the page's own origin and carries `X-Tandem-CSRF`. `/v1/auth/users`, `/v1/auth/sessions` and `/v1/auth/password` manage accounts and sessions; the last enabled owner cannot be disabled, demoted or removed. Failed sign-ins are limited per address and per name, and each event is an audit row with no secret in it. With the switch off every route answers as before.
- With `TANDEM_AUTH=accounts` (SEC-26, SRV-865): a bare process bound to loopback with no password lets this machine's browser in as the owner `local` (local mode) and nobody else; bound beyond loopback, in a container (`TANDEM_DEPLOY`), on Kubernetes, behind a proxy (`TANDEM_LOCAL_MODE=off`) or with a password, nothing answers without a session or a token but `/health`'s status, the page shell, the sign-in and the setup. The first owner is made at `POST /v1/auth/setup` with a one-time code of 20 characters (5 tries, 24 hours) that each start logs while no owner exists, `tandem-app users setup-code` prints, or a mounted file holds (`TANDEM_SETUP_CODE_FILE`). `tandem-app users list|add|disable|enable|role|reset-password|remove|setup-code` manages accounts on the machine; `add` and `reset-password` print a one-time code that only sets a password. The page shows a sign-in, a first-run screen and the password step, and sends `X-Tandem-CSRF` on every write. The installer takes `--behind-proxy` and prints a setup code instead of writing an admin token. On the first start `admin.json`'s password becomes the account `owner` and `admin.json` follows its password from then on, so the release before still signs in after a rollback; with only an admin token, the token is the setup code once. A leftover or malformed legacy variable is a health finding, never a stop; the old page's sign-in form signs in as that owner.
- Health is a page under Monitor (SRV-835). Its first sentence says how things stand; below it one card each for this TandemApp, every engine host, the plugins and the pairing codes refused in the last ten minutes. A card draws its checks in the order they ran, so the place where the line breaks is the place to look, lists its findings worst first with the controller's sentence and fix, and folds the checks that passed. A button runs what TandemApp can fix itself: Start, Rotate the token, Restart chatd, and Upgrade, which shows the engine host's plan before anything changes. Other buttons check again or show the steps. A changed host key shows both fingerprints and how to pair again; nothing on the page connects past it. The page reads again every 20 seconds, follows a fix until it settles, asks for the admin password when a fix needs it and waits when a target had too many fixes. Add engine and the settings pages link to it.
- Hooks and decision providers have pages under Settings, Hooks (VIS-282). The pipeline shows a request's 15 stages in order with the hooks at each, and how much of the 800 ms before the first token they use; arrows and dragging change the order. Add a hook walks through the stage, the role, the scope, the failure policy and the payload level, then shows a webhook's secret once with the code that checks a signature. A hook's page has its breaker, figures, calls, the secret's rotation and a playground that sends the stage's sample event. Trace shows one request across every stage. Decision providers shows who answers each question, each provider's health and mode, and the agreement report with on, shadow and both A/B sides next to each other. The switches are staged and go through the settings' review. Replay is not built, and the Trace page says so.
- A plugin SDK for Python (SRV-861): `sdk/python/tandemapp_plugin`, the standard library only, turns a plugin into decorated tools (the four MCP annotations required, strict input schemas checked), hooks, decision providers by question and backends, with its settings, secrets and engine requests, and refuses to start when the code and plugin.json differ. `tandemapp-plugin new` starts a plugin of each kind with a copy of the SDK. Two examples are built on it, `note-webhook` (an observer hook and a tool posting notes to a webhook) and `keyword-router` (a decision provider for classify and judge); the tests install and run both through the plugin host, sandboxed and at trust host, and the vLLM and SGLang engine-stats manifests through the installer. [docs/plugins-sdk.md](docs/plugins-sdk.md) has the API.
- Plugins are signed and trusted (SEC-18): `tools/plugin_sign.py` makes an ed25519 key and signs a plugin folder (a statement naming the plugin, its version, the sha256 of its tree and of its manifest), never printing the private key. `/v1/fleet/plugin-trust` holds the publisher keys this TandemApp trusts, each added and removed with its fingerprint typed back and optionally limited to plugin ids and trust levels, and the policy to require a trusted signature for sandboxed plugins (off by default). A tree or signature that changed after the install is refused at enable and load, with the reason and a health finding. Trust host takes a signature by a trusted key or the plugin's id typed; trust engine takes both, per engine host, and still does not run until the in-process chain exists. An upgrade that asks more trust waits for the typed confirmation while the installed version keeps running. Every trust decision is audited. [docs/plugins.md](docs/plugins.md#trust) has the rules.
- Plugins run (SRV-859): the controller's plugin host starts each enabled plugin as one process speaking MCP over stdio plus `hooks/call`, `decision/ask` and `backend/request`, in a container or pod of the chat sandbox's class by default (its tree read-only, no network but the egress proxy, which passes only the hosts of its granted `network:` capabilities and never this box, a link-local address or the Kubernetes API), or as a process of the app's user once the admin granted it trust host; trust engine is refused until it exists. While it runs its tools are offered to the Chat tab, its hooks join the runner, its decision providers watch in shadow, its backends join the backends store, its skill folders the conductor's and its panels are served in a sandboxed frame with a bridge limited to its capabilities; all of it goes when it stops. Hooks and decision providers of kind `plugin` name a plugin's hook or provider to set its priority, scope or mode. Each capability is checked at its use and a refusal is journaled. A plugin that fails five times within an hour is disabled and named on the health page, as is one with no sandbox runtime. Status, logs (secrets replaced), start, stop and restart are on `/v1/fleet/plugins/<id>/*`. [docs/plugins.md](docs/plugins.md#running-plugins) has the rules.
- Plugins, part one (SRV-857): `contracts/plugin-v1` defines a plugin's manifest (`plugin.json`: name, version, the TandemApp range, the hooks API, the entry command, its contributions, a settings schema, secrets and capabilities) with examples, refusal fixtures and a validator (`tools/plugin_check.py`). `/v1/fleet/plugins` inspects and installs a plugin from a folder, a wheel or a git commit without running any of it, records the sha256 of its files and checks it again on enable, refuses a tool without its four MCP annotations or with input that allows extra properties, refuses an incompatible TandemApp or hooks API with the needed version, and enables, disables, upgrades (keeping what the new schema allows) and removes (not while a hook names it). A plugin's settings, secrets and capability grants are the settings interface's new `plugins` scope (settings-v1 1.1): deny by default, pairing's rights for a grant, a second confirm for full prompts, engine control and a host outside the LAN. One generator turns a JSON schema into a form for the page (`proxy/schemaform.py`, `dashboard/src/lib/schema-form.ts`). [docs/plugins.md](docs/plugins.md) has the rules.
- One settings interface over the existing stores (SRV-845): `/v1/settings` answers schema, values, plan, apply, versions and restore for the scopes app (the page's switches), backends (backends, routes, users), conductor (its documents), engine (each paired engine host's overlay over SSH, hot keys over HTTP) and hooks (an adapter, empty until the hook registry plugs in). A change set spans scopes, applies in that order with one confirm (a second one for a key that feeds an engine's disk-cache fingerprint), stops at the first failure and says what applied and how to restore it. An engine change that needs a restart drains that engine's backends (503 with Retry-After) while its job waits for idle, then warms it with one token; a countdown and a cancel go with it. Secrets are write-only. Every change is an audit row with the change set's id. [docs/settings.md](docs/settings.md) and `contracts/settings-v1` have the rules.
- Chat sandboxes can run as Kubernetes pods (SRV-863): with the Helm chart's `sandbox.mode: kubernetes` chatd makes each chat's sandbox a pod in the release's namespace through the API (a Role of pods, exec and logs there), with today's lockdown and limits, a user namespace and a 512-process limit per pod, the chat's folders as subPath mounts of the release's volume, and no network but chatd's egress proxy (a NetworkPolicy; chatd checks at start that the cluster enforces it and offers no sandbox when it does not). An out-of-memory kill, an eviction, a pod with no room and an image the node lacks each say so on the call; orphan pods go at start and once a minute. `ops/sandbox/build-k8s.sh` builds the image inside the cluster and imports it on the node, with no registry. [docs/chat.md](docs/chat.md#sandboxes-as-kubernetes-pods) and the chart's README have the design.
- A sandbox killed at its memory limit says "out of memory" on Podman and containerd too: chatd reads the kill count from the cgroup the container's first process is in, not only from Docker's two layouts.
- A Split starts and serves from TandemApp (SRV-817): one model cut across two Sparks. The planner asks each Spark's engine for its estimate with the `split` block (engine API 1.2), picks the cut whose smaller headroom is largest, and states every number, the link and why each other cut lost. The two Sparks need an interface pair in one subnet: a fabric pair first, a LAN pair with a warning, because the data link is neither signed nor encrypted after its handshake. A start hands a link key to both node agents (each keeps it in a 0600 file), starts the front stage, then the tail, checks both stages and the link, and routes requests to the tail alone. A link that drops makes the deployment degraded: requests get 503 `stage_down` with `Retry-After` until the stages link again by themselves. Stop takes the tail first and removes the key. The controller does not switch a Spark's weight profile: set each Spark to the pack first. [app/docs/proxy.md](docs/proxy.md) has the rule and the states.
- The Models page shows a Split as two stage bars with the link between them, its plan before the start, and plain words for the degraded and half-running states (VIS-272). Simple and Advanced choose how much of the plan shows.
- The standalone dashboard and proxy is TandemApp, and its command is `tandem-app` (OPS-238). `tandem-dash` still runs it with the same arguments and exit codes, after one line on stderr, and is removed in 0.17.0. The image is `tandemllm-app` from `app/packaging/Dockerfile.app`, its volume `tandem-app` and its env file `app/packaging/app.env.example`; [app/docs/proxy.md](docs/proxy.md#in-docker) says how to mount or copy a `tandem-dash` volume.
- The OpenAI routes can run through TandemApp's controller in front of the engine (SRV-733): `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/responses` and `/v1/models` answer as the engine does (its cards and decision models, any model id with `TANDEM_DEFAULT_BACKEND`, the client's headers on, the engine's keys with `TANDEM_API_USERS_FROM`), a request the engine still works on is never cut by the relay's timeouts, and each request is one row of the controller's ledger with its Spark, joined to the engine's row by the answer id (ledger schema 12). [app/docs/proxy.md](docs/proxy.md#the-data-plane-clients-through-the-controller) has the reverse proxy's locations and the rollback.

### TandemApp in its own directory

- TandemApp is its own package in `app/` (SRV-747): the distribution `tandemapp`, with its own version in `app/VERSION` (0.15.0; `tools/release.sh` writes it next to `VERSION` while one release ships both), installed from a checkout with `pip install ./app`, or `pip install './app[host]'` for psutil and NVML. The root `pyproject.toml` is gone. TandemApp's code imports nothing from the engine (`server/`, `engine/`), and `app/tests/test_import_boundary.py` holds that (SRV-748).
- The API TandemApp uses from the engine is a contract the engine owns, `contracts/engine-api-v1` (TandemApp pins a copy to an engine commit): the routes, `/health`, the engine's own reads, its metrics, its tool-call parsing, the Setup Guide's estimate cases and limits, and TandemNode's control of the engine. The engine's `/health` carries `engine_api` (`1.3`: 1.1 adds `GET /v1/replica/identity`, 1.2 the estimate's optional `split` block and `/health`'s optional `stage` block of a split model, 1.3 moves the contract to the engine and marks the routes that leave it, with no answer changed); an engine that does not send it speaks 1.0, and TandemApp takes any 1.x. Beside it, `contracts/engine-ext-v1` 1.0 is the interface for code that runs inside the engine's process (TandemApp's conductor in chat mode): closed at start, open per request.
- A Replicas deployment checks its members (SRV-741): each engine's identity (engine API 1.1) through TandemNode, every field but the window compared, a member that differs is `mismatch` and the field is named; an output canary every 10 minutes and after any member change, where a near tie counts only as a warning when one engine flips on it itself; a request past one member's window goes to a member that fits, else 400; `/v1/cache/peek`, `/prewarm` and `/release` go to the member that holds the conversation. An engine on 1.0 keeps the release and weights check. [app/docs/proxy.md](docs/proxy.md#deployments-placement-and-weights) has the rules.
- A deployment names the engine API version it needs: a member whose engine speaks another major is `down`, and the node's engine view `unhealthy`, with a reason that names the major this TandemApp needs; starting a deployment on such an engine fails at once.
- TandemNode's placement estimates come only from the engine's Setup Guide (`/v1/setup/estimate`). Add Spark's check reads TandemNode's version only, so a box with an engine checkout and no TandemNode reads `not installed`.
- Add Spark's engine step and the fleet update take the engine installer from `TANDEM_ENGINE_INSTALL_SH` only. The engine ref is `TANDEM_ENGINE_REF`, else `v` and the `VERSION` file beside the installer, else `v` and TandemApp's release. Without the variable, Add Spark's engine step fails and names it, and the fleet update skips each node's engine step.
- Node wheels are named `tandemapp-*.whl`.
- The `tandem-dash` alias stays until TandemApp 0.17.0, counted on `app/VERSION`.
- TandemApp's tests live in `app/tests` with their own runner, `app/tests/script_suite.py`. Since OPS-250 GitHub runs them in TandemApp's own `tests` workflow, as the `app suite` check, with `.[host]` installed and no torch; the engine's CI no longer runs them.
